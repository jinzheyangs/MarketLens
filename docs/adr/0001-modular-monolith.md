# ADR-0001：阶段 1 采用模块化单体

- 状态：已接受
- 日期：2026-11-23
- 关联阶段：1

## 背景

蓝图最终包含 API、身份授权、RAG、采集、Agent 编排、证据报告与运营治理。阶段 1
需要先建立可测试、可部署的工程底座，同时不能破坏后续拆分与演进。过早拆分微服务会
引入分布式事务、服务发现、跨服务鉴权和本地开发复杂度，而当前没有独立扩缩容证据。

## 决策

- 采用单部署单元、模块化分层的 Python 应用：`api` → `services` → `db`，跨层基础
  设施在 `core`。
- FastAPI 应用由 `app.factory.create_app` 装配；`app.main` 只暴露 ASGI `app`，便于
  测试使用显式 Settings 构建独立实例。
- 所有业务数据通过 SQLAlchemy ORM/仓储访问，不在路由中拼接 SQL。
- 异步 I/O 使用 asyncpg/SQLAlchemy async；连接池、语句超时、连接建立超时均显式配置。
- 暂不引入消息队列、Temporal 或微服务拆分；按蓝图阶段 7 再引入。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 模块化单体 | 事务简单、本地开发轻、边界可按模块约束 | 单进程扩展 | 采纳 |
| 立即拆微服务 | 独立部署 | 分布式一致性与鉴权成本高、无规模依据 | 拒绝 |
| 单文件/无分层 | 起步快 | 无法承载多租户、审计、RAG 演进 | 拒绝 |

## 后果

- 正面：迁移、事务、测试和部署简单；后续可按模块边界拆分。
- 负面：团队需要严格遵守分层与模块边界，避免形成隐式耦合。
- 安全：所有入口共享同一中间件与异常模型，便于统一执行租户/日志/限制策略。
- 后续：阶段 7 若拆分，模块边界与服务契约必须先稳定；届时通过 outbox/事件解耦。

## 验证

- 工厂可创建多个独立应用实例供测试。
- 单元测试不依赖数据库；集成测试在 PostgreSQL 上验证迁移与租户写入守卫。
- CI 执行 lint、类型检查、迁移往返和测试。
