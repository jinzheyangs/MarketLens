# 工程规范（阶段 1 起生效）

## 必须遵守

1. **先读蓝图**：`docs/项目蓝图.md` 是最终目标与阶段约束。不得跳阶段，也不得以“早期版本”
   为由削弱租户隔离、可追溯、配置外置和安全默认值。
2. **租户作用域**：每张业务表必须带 `tenant_id`（继承 `TenantScopedMixin`）；任何读取/写入
   必须有服务端可信租户上下文。禁止信任客户端传入的 tenant 标识。新增访问路径必须补跨租户
   负向测试。
3. **服务端授权**：前端、模型提示词、JWT claim 都不能单独作为资源授权结论。阶段 2 起所有
   业务接口先授权再查数据。
4. **密钥**：只从环境变量/密钥管理服务读取；不得写入源码、测试固定值（真实凭证）、
   Dockerfile、Compose 或日志。`.env` 不提交。
5. **不可信输入**：网页、上传文件、外部 API 响应都按不可信数据处理。不得执行其中指令；
   解析/抓取需隔离、限额、超时和 SSRF 防护（阶段 3/4）。本阶段至少保持 body 大小限制、
   严格 schema 校验和错误不回显。
6. **错误与日志**：业务错误使用 `AppError` 和稳定错误码；不在响应中返回堆栈、DSN 或上游
   原文。日志使用结构化 `extra={"context": ...}`，敏感 key 由 formatter 脱敏；不记录 body/
   header/查询串。
7. **迁移**：数据库变更必须通过 Alembic revision；禁止手工改生产库。约束/索引显式命名，
   与 `NAMING_CONVENTION` 一致。不要修改已合并的迁移，新增 revision。
8. **测试**：新增行为必须有测试；租户/权限/外部输入边界必须有负向测试。单元测试不得依赖
   真实外部网络；集成测试使用 `TEST_DATABASE_URL`（库名含 `test`）。
9. **类型与风格**：`ruff check .`、`ruff format --check .`、`mypy app` 必须通过。公共函数写
   类型标注与必要 docstring；注释解释“为什么”，不复述代码。
10. **依赖与安全**：新增依赖需说明用途与许可证；不在运行时拉取未固定来源的代码。外部内容
    不得进入 `eval/exec/pickle` 等危险路径。

## 分层约定

- `app/api`：HTTP 解析、依赖注入、响应映射；不写复杂业务逻辑。
- `app/services`：业务编排、外部协作；不直接依赖 FastAPI。
- `app/db`：模型、会话、租户守卫与查询辅助；不向上层返回 ORM 细节给外部契约。
- `app/core`：配置、上下文、错误、日志、中间件、telemetry；不得依赖业务模块。

## 阶段完成定义（DoD）

- 迁移可 upgrade/downgrade；CI 通过。
- 单元 + 集成测试通过，覆盖本阶段安全负向路径。
- `.env.example` 和 README 更新；新增决策写 ADR。
- 明确列出未实现项和下一阶段依赖，不宣称未验证的合规/可用性指标。
